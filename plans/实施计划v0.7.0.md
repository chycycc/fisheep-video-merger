# Fisheep Video Merger — 前端架构演进计划 (v0.7.0 及以后)

## 背景剖析：当前前端架构的“技术债务”
目前项目前端采用 **原生 HTML/CSS + Alpine.js + 原生 JS** 的混合形态。

### 优势（为何保留至今）：
1. **零构建环境 (Zero-build)**：无需 Node.js 和复杂的 Webpack/Vite 打包链路。极其契合 `pywebview` 本地客户端的轻量化分发，PyInstaller 打包体积小且路径解析简单。
2. **极速冷启动**：原生解析，无虚拟 DOM (Virtual DOM) 初始化开销，软件打开即用。

### 劣势（亟待解决的痛点）：
1. **CSS 样式脆弱性（破窗效应）**：千行规模的手写 `style.css` 依赖人工记忆变量名。一旦 CSS 变量错位、`z-index` 堆叠混乱或全局样式污染，极难排查与维护。
2. **状态管理割裂**：虽然引入了 Alpine.js，但在部分紧急修复（如弹窗干预、旧版逻辑）中，仍然存在 `document.getElementById('xxx').style.display = 'none'` 这样的原生 DOM 暴力操作。“数据驱动”与“手动操纵 DOM”混杂，是产生状态不同步 Bug 的温床。

## 渐进式升级演进路线

针对当前“FFmpeg 核心调度为主，UI 为壳”的项目定位，推倒重来（直接上 Vue/React）成本过高且破坏轻量化优势。建议采取以下三阶段渐进式演进：

### 🟢 阶段一：规范化 Alpine.js 数据驱动 (高性价比，建议紧接在 v0.7.0 执行)
**核心目标**：彻底消灭命令式 DOM 操作，实现 UI 与逻辑 100% 解耦。
- **操作方案**：将散落在 `app.js` 中的底层 DOM 操作（如修改 `textContent`、改变 `classList`、控制显示隐藏），全盘重构为 Alpine.js 声明式指令（`x-data`, `x-show`, `x-text`, `x-bind:class`）。
- **零成本**：不需要引入任何新依赖，不改变打包流程。
- **预期收益**：后续新增任何复杂交互（确认弹窗、队列动画），只需在 Python 传值或 JS 中修改变量状态，界面自动且安全地响应，彻底阻断因为遗漏 DOM 更新导致的 UI Bug。

### 🟡 阶段二：引入 TailwindCSS (Standalone CLI) (现代化重构，建议在 v0.8.0 执行)
**核心目标**：抛弃千行手写 `style.css`，建立工业标准的设计规范，同时保持零 Node.js 依赖。
- **操作方案**：采用 Tailwind 官方提供的**独立免安装二进制 CLI 工具**。在 HTML 中直接编写 Utility Classes（如 `class="bg-blue-500 rounded-lg shadow-md"`），CLI 实时扫描并生成一个极致压缩的专属 CSS 文件。
- **预期收益**：消灭自行维护 CSS 变量的心智负担，强制拉平所有组件的间距、颜色、阴影标准，让 UI 达到高度统一的现代化质感。

### 🔴 阶段三：引入全链路前端工程化 (Vue/React + Vite) (远期预案)
**核心目标**：应对指数级上升的前端交互复杂度。
- **触发条件**：仅当未来需要实现诸如“多轨道视频时间轴拖拽裁剪”、“复杂的实时流媒体波形预览”、“高频实时图表看板”等功能时启用。
- **操作方案**：前端独立为独立工程经 Vite 产出静态文件，Python 后端（如 FastAPI/Flask 微服务架构）启动本地 HTTP Server 提供给 Webview 渲染。
- **代价**：彻底打破目前的极简单体结构，大幅增加环境配置成本及 PyInstaller 跨平台打包的路径容错难度。

## 结论与行动建议
对于 `Fisheep` 工具箱，核心技术壁垒始终是 **FFmpeg 进程防阻塞调度与匹配算法**。
当前最务实的决策是：**冻结阶段三，立刻执行阶段一，并论证阶段二。**

接下来的改动将聚焦于：花时间清扫 `app.js` 中的原生 DOM 操作，将其收编进 Alpine 的 `x-data` 响应式树中，夯实界面稳定性。

## 补充剖析：组件化与代码重复率问题 (DRY 原则违背)

**客观诊断结论：当前前端严重不符合现代开发标准，充斥着大量冗余代码。**

在 `index.html` (接近 1000 行) 和 `app.js` (接近 2500 行) 中：
1. **HTML 视图的高度重叠**：音视频合并、格式转换、提取音频、视频压缩、视频裁剪这 5 个工具页，内部的“拖拽上传区域 (`file-drop-area`)”、“文件列表 (`task-list`)”、“底部操作栏 (`action-bar`)” 几乎是完完全全的复制粘贴。如果要修改一个按钮的边距，必须在 5 个地方同时修改，极易遗漏。
2. **违背前端组件化标准**：业务逻辑与 UI 被打成了面条代码（Spaghetti Code），全局变量泛滥，缺乏模块化（Module）和组件化（Component）的物理隔离。

### 无 Node.js 环境下的“轻量化组件方案”

既然我们坚持**不引入 Vue/React/Vite 打包链**，我们要如何实现组件化？

- **方案 A：原生 Web Components (Custom Elements)**
  利用浏览器原生支持的 `<file-drop-area>` 或 `<task-list>` 自定义标签，配合原生 JS 封装 Shadow DOM。
  *评价：学习曲线陡峭，与 Alpine.js 结合容易产生作用域冲突，暂不推荐。*

- **方案 B：原生 ES Modules + 动态模板异步加载 (极度推荐的纯前端方案)**
  既然要**坚决维护前后端分离**，同时又不想引入 Node.js/Vite，我们可以充分利用现代浏览器（webview）的原生能力：
  1. **JS 逻辑组件化**：废除 2500 行的 `app.js`，采用原生 `<script type="module">`，将代码拆分为 `merger.js`、`converter.js` 等独立文件，通过 `import`/`export` 组织代码。
  2. **HTML 结构组件化**：利用原生 JS 的 `fetch()` API 或 Alpine.js 的拓展能力，实现运行时的异步组件注入。例如：`<div x-html="await (await fetch('./components/task-list.html')).text()"></div>`。
  *评价：最符合现代标准！彻底实现前端的 HTML/JS 高度内聚与低耦合，且完全不需要 Vite 环境。*

- ~~**方案 C：Python Jinja2 服务端模板渲染**~~ *(已否决)*
  *评价：虽然降低了前端开发难度，但会导致前端 UI 结构和 Python 后端产生极强的强耦合，违反了界面的独立演进原则，不予考虑。*
